# DTO Mapping

Freezed DTOs with JSON serialization and `toDomain()` conversion.

---

## Rules

1. `@freezed abstract class XDto with _$XDto` -- Freezed with JSON support
2. `const XDto._();` -- private constructor required for instance methods (`toDomain()`)
3. `factory XDto.fromJson(Map<String, dynamic> json) => _$XDtoFromJson(json);` -- generated deserializer
4. `XDomain toDomain()` -- manual mapping to domain entity
5. Import domain barrel for entity reference
6. `part '<name>.freezed.dart';` and `part '<name>.g.dart';` -- code generation parts
7. After creating: run `make gen` and add to `models/models.dart` sub-barrel
8. **Field ordering in factory constructor** (strict):
   - **Required non-nullable** fields (`required Type field`) — alphabetically
   - **Optional with defaults** (`@Default(value) Type field`) — alphabetically
   - **Nullable** fields (`Type? field`) — alphabetically

## Entity vs DTO Comparison

| Aspect | Entity (domain) | DTO (data) |
|--------|----------------|------------|
| Location | `domain/entities/` | `data/models/` |
| JSON | No | Yes (`fromJson`, `toJson`) |
| `toDomain()` | N/A | Yes |
| Private constructor | No | Yes (`const XDto._()`) |
| Imports | `freezed_annotation` only | `freezed_annotation` + domain barrel |
| Part files | `.freezed.dart` | `.freezed.dart` + `.g.dart` |
| Purpose | Business logic | API communication |

## Freezed Field Ordering (Strict)

All fields in Freezed factory constructors must follow this exact order:

1. **Required non-nullable fields** (`required Type field`) — sorted alphabetically
2. **Optional fields with defaults** (`@Default(value) Type field`) — sorted alphabetically
3. **Nullable fields** (`Type? field`) — sorted alphabetically

**Example:**

```dart
@freezed
abstract class UserDto with _$UserDto {
  const factory UserDto({
    // 1. Required non-nullable (alphabetically)
    required String email,           // 'e' first
    required String id,               // 'i' second
    required String name,             // 'n' last

    // 2. @Default non-nullable (alphabetically)
    @Default(false) bool isActive,    // 'i' first
    @Default(0) int loginCount,       // 'l' second

    // 3. Nullable (alphabetically)
    String? avatarUrl,                // 'a' first
    DateTime? lastLoginAt,            // 'l' second
  }) = _UserDto;

  const UserDto._();

  factory UserDto.fromJson(Map<String, dynamic> json) =>
      _$UserDtoFromJson(json);

  User toDomain() {
    return User(
      id: id,
      email: email,
      name: name,
      avatarUrl: avatarUrl,
    );
  }
}
```

**Why this ordering?**
- **Deterministic**: Same input always produces same output structure
- **Readable**: Most important (required) fields come first
- **Searchable**: Alphabetical order makes fields easy to find

**Common mistakes:**

```dart
// ❌ WRONG -- nullable before required
const factory UserDto({
  String? avatarUrl,         // Should be last!
  required String id,        // Should be first!
}) = _UserDto;

// ❌ WRONG -- not alphabetically sorted within group
const factory UserDto({
  required String name,      // Should be last in required group!
  required String email,     // Should be second!
  required String id,        // Should be first!
}) = _UserDto;

// ✅ CORRECT -- required alphabetically, then nullable alphabetically
const factory UserDto({
  required String email,
  required String id,
  required String name,
  String? avatarUrl,
}) = _UserDto;
```

## Anti-Patterns

### WRONG: DTO without `toDomain()`

```dart
// WRONG -- DTO must convert to domain entity
@freezed
abstract class UserDto with _$UserDto {
  const factory UserDto({required String id, required String name}) = _UserDto;
  factory UserDto.fromJson(Map<String, dynamic> json) => _$UserDtoFromJson(json);
  // Missing toDomain()!
}
```

### WRONG: Entity with JSON

```dart
// WRONG -- entities must not have JSON serialization
@freezed
abstract class User with _$User {
  const factory User({required String id}) = _User;
  factory User.fromJson(Map<String, dynamic> json) => _$UserFromJson(json); // WRONG
}
```

### WRONG: Missing private constructor

```dart
// WRONG -- toDomain() requires private constructor
@freezed
abstract class UserDto with _$UserDto {
  const factory UserDto({required String id}) = _UserDto;
  // Missing: const UserDto._();
  User toDomain() => User(id: id); // WON'T COMPILE
}
```

## JSON -> DTO -> Entity Transformation

End-to-end flow from raw JSON to domain entity:

```
Raw JSON (API response)
  │  {"id": "1", "title": "Hello", "author_id": "42", "created_at": "2024-01-01T00:00:00Z"}
  ▼
PostDto.fromJson(json)           ← Generated by json_serializable
  │  PostDto(id: '1', title: 'Hello', authorId: '42', createdAt: DateTime(2024))
  ▼
postDto.toDomain()               ← Manual mapping method
  │  Post(id: '1', title: 'Hello', authorId: '42', createdAt: DateTime(2024))
  ▼
Post entity (used by controller/UI)
```

In code (inside repository):

```dart
final Response<Map<String, dynamic>> response = await _dio
    .get<Map<String, dynamic>>('${ApiEndpoints.posts}/$id');
final PostDto dto = PostDto.fromJson(response.data!);  // JSON -> DTO

return dto.toDomain();  // DTO -> Entity
```

For lists:

```dart
final List<PostDto> dtos = await _remoteDataSource.getPosts();

return dtos.map((PostDto dto) => dto.toDomain()).toList();
```

## Request DTOs

Request DTOs are used for POST/PUT request bodies. They have `toJson()` but NO `toDomain()`.

```dart
// lib/features/auth/data/models/sign_in_request.dart
@freezed
abstract class SignInRequest with _$SignInRequest {
  const factory SignInRequest({
    required String email,
    required String password,
  }) = _SignInRequest;

  factory SignInRequest.fromJson(Map<String, dynamic> json) =>
      _$SignInRequestFromJson(json);
}
```

**Key differences from response DTOs:**
- No `const XRequest._();` -- no instance methods needed
- No `toDomain()` -- request DTOs don't map to domain entities
- `fromJson` is still generated (required by Freezed) but typically unused
- `toJson()` is auto-generated and used in datasource: `data: request.toJson()`

See also: `lib/features/auth/data/models/sign_up_request.dart`

## @JsonKey Usage

### Global Configuration

The project's `build.yaml` configures `json_serializable` globally:

```yaml
# build.yaml
targets:
  $default:
    builders:
      json_serializable:
        options:
          explicit_to_json: true
          field_rename: snake
```

This means:
- All fields are automatically converted to `snake_case` in JSON
- Nested objects use their `toJson()` method during serialization

### When to Use @JsonKey

```dart
// Field matches snake_case convention -- NO @JsonKey needed
required String authorId,     // JSON: "author_id" (automatic)

// Field differs from snake_case -- USE @JsonKey
@JsonKey(name: 'user_uuid')
required String id,            // JSON: "user_uuid" (override)

// Default value for optional fields
@JsonKey(defaultValue: 0)
required int likeCount,
```

## Nested DTOs

When a DTO contains another DTO, both must have `fromJson`. Nested `toJson()` calls are handled automatically by `explicit_to_json: true`.

```dart
@freezed
abstract class OrderDto with _$OrderDto {
  const factory OrderDto({
    required String id,
    required UserDto user,        // Nested DTO
    required List<ItemDto> items, // List of nested DTOs
  }) = _OrderDto;

  const OrderDto._();

  factory OrderDto.fromJson(Map<String, dynamic> json) =>
      _$OrderDtoFromJson(json);

  Order toDomain() {
    return Order(
      id: id,
      user: user.toDomain(),
      items: items.map((ItemDto i) => i.toDomain()).toList(),
    );
  }
}
```
